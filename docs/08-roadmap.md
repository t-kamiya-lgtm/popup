## 2. 主要な設計上の意思決定と根拠

| 決定 | 根拠 | 代替案と却下理由 |
| --- | --- | --- |
| 設定を CDN に全量配信し判定はクライアント | 往復ゼロで表示遅延を排除。CDN で全ユーザー共通キャッシュ可 | 毎回サーバ判定 → レイテンシと負荷、キャッシュ不可 |
| **PostgreSQL 一本**（ClickHouse / Redis / キューを使わない） | 月間 1 万 PV = imp 2,000 件/月。分析 DB は運用コストが価値を上回る。100 倍まで現構成で耐える | 当初案の ClickHouse + Redis + キュー → この規模では過剰設計。障害点と運用負荷だけが増える |
| クリエイティブ割当を **sessionId のハッシュ**で決定 | サーバ状態ゼロで均等・セッション内一貫。アプリ停止中も配信継続 | Redis カウンタ → Redis 依存と往復が増える / 純粋な乱数 → リロードで別バナーが出る |
| **`pz_t` によるリンク装飾**でドメイン跨ぎ CV を計測 | クリックはこちらが URL を発行する遷移なので 100% 引き継げる | Cookie 共有 → 別ドメインでは不可 / 確率的突合 → 精度が担保できない |
| 商品コードを**タグから受領**し集計の一次キーにする | カート側マスタと必ず一致。URL ルールの設定ミス起因の集計ズレが消える | URL パターンで商品を推測 → メンテ負荷と誤集計のリスク |
| **RLS でテナント分離を DB レベルに強制** | SaaS ではアプリ層の書き漏らし 1 箇所が越境事故になる | アプリ層の WHERE 句のみ → レビュー漏れが致命傷になる |
| Shadow DOM (closed) | 顧客サイト CSS との相互汚染をゼロにする | iframe → 高コスト・レスポンシブ調整が困難 |
| renderer を SDK と管理画面で共有 | プレビューと本番の乖離を構造的に排除 | 管理画面で別実装 → 見た目のズレが恒常的なバグ源になる |
| 対照群を最初から設計に入れる | 「本当に増えたか」は差分でしか測れない | クリック経由 CV のみ → 効果を過大評価する |
| ブラウザバックは 1 回のみトラップ | ダークパターン回避・ブラウザのペナルティ回避 | 無限トラップ → UX 毀損、離脱率悪化 |
| 集計はロールアップ参照 | レポート応答を安定させる | 生イベント直クエリ → データ増でタイムアウト |

## 3. リスクと対策

| リスク | 影響 | 対策 |
| --- | --- | --- |
| SPA サイトで `pushState` 競合 | 顧客サイトのルーティング破壊 | 自前 state を判別。サイト単位で `exit_back` を無効化できる設定を用意。導入時に検証手順を提供 |
| 顧客サイトの JS エラーに巻き込まれる | サイト全体が壊れたように見える | 全エントリポイント try/catch、例外時は自己 teardown、Sentry へ送信 |
| 広告ブロッカーによる計測欠損 | 実績が過小に見える | 計測ドメインを 1st-party サブドメイン CNAME にできる構成。欠損率の推定値を管理画面に表示 |
| ITP による CV ウィンドウ短縮 | Safari で CV が取りこぼされる | S2S CV API を提供。管理画面で注意喚起 |
| **カートが別ドメインでビュースルー CV が取れない** | 効果を過小評価する | 対照群を Phase 1 必須に。レポートで列を非表示にし誤読を防ぐ |
| **差し込み変数が未展開のまま送信される**（`{{注文番号}}` が文字列で届く） | 全 CV が同一 orderId になり 1 件しか計上されない | タグ側で `{{` の残存を検知して送信中止。テスト購入で実出力値を必ず確認 |
| **母数不足で誤った意思決定をする** | 効果のないクリエイティブを採用 | CV 30 件未満に「参考値」バッジ。判断は CTR ベースへ誘導。有意差判定に必要な期間を明示 |
| テナント間のデータ越境 | SaaS として致命的 | RLS + 全エンドポイントの越境テスト + RLS 未設定検出の CI チェック |
| ポップアップによる Core Web Vitals 悪化 | 顧客サイトの SEO 影響 | fixed レイヤのみで CLS 0、LCP 確定後にロード、Lighthouse 検証を CI に組込み |
| Google の「煩わしいインタースティシャル」ペナルティ | 顧客サイトの検索順位 | 初期表示直後の全画面表示を禁止（最短 3 秒待機のバリデーション）、SP は画面の 30% 以下を推奨としてガイド |
| 顧客サイトからのなりすまし計測 | データ汚染 | `allowed_hosts` 検証、レート制限、署名付き設定バージョン |
| イベント量増によるコスト増 | 運用コスト | サンプリング（imp のみ）を将来オプションとして用意、13 ヶ月で生ログ削除 |

## 4. リポジトリ構成（案）

```
popup/
├─ apps/
│  └─ web/              Next.js 単一アプリ
│     ├─ (admin)/       管理画面
│     ├─ api/           管理 API
│     ├─ c/[siteId]/    配信設定 JSON（CDN キャッシュ）
│     ├─ e/             計測エンドポイント
│     └─ cron/          日次集計
├─ packages/
│  ├─ loader/           t.js
│  ├─ sdk/              sdk.js（full / cart モード）
│  ├─ renderer/         描画（SDK と admin プレビューで共有）★
│  ├─ shared/           型定義・マッチャ・ローテーション・署名（全レイヤ共有）★
│  └─ image/            最適化パイプライン
├─ db/
│  ├─ migrations/
│  └─ policies/         RLS ポリシー
├─ e2e/                 Playwright（EC モックサイト + カートモックで検証）
└─ docs/
```

★ の 2 パッケージが品質の要。

- `renderer`: プレビューと本番の描画が同一コードになり、見た目の乖離が構造的に起きない
- `shared`: **URL / 商品コードのマッチ判定・クリエイティブのローテーション・
  `pz_t` の署名フォーマット**を一箇所に置く。管理画面のマッチ判定ツール、SDK の配信判定、
  サーバ側の検証がすべて同じコードを通るため、
  「管理画面ではマッチしたのに配信されない」「プレビューの配信比率と実績が合わない」が起きない

## 5. テスト方針

| レイヤ | 手法 |
| --- | --- |
| URL / 商品コードマッチャ、フリークエンシー、アトリビューション | ユニットテスト（境界値重点） |
| 均等配信 | ランダムな sessionId 10,000 件で偏りが ±3% 以内（クリエイティブ 2〜5 件で検証） |
| テナント分離 | 全エンドポイントで他テナントの ID を指定し 404 を確認。RLS 未設定検出の CI チェック |
| ドメイン跨ぎ CV | カートドメインを模した別オリジンのモックページで `pz_t` の受け渡しを E2E 検証 |
| `pz_t` の署名 | 改ざん・期限切れ・他サイト鍵での偽造をすべて拒否することを検証 |
| SDK 表示 | Playwright で PC/SP viewport × 位置 4 種のビジュアルリグレッション |
| トリガー | Playwright で `goBack()` / タイマー / mouseout を実行し発火を検証 |
| 計測 | モックサーバでイベントペイロードを検証。重複排除の冪等性テスト |
| 集計 | 既知イベント列 → 期待ロールアップ値のゴールデンテスト |
| 性能 | Lighthouse CI でタグ有無の LCP / CLS 差分を監視 |

## 6. 次に決めるべきこと

### 解決済み

| 論点 | 決定 |
| --- | --- |
| 「期間指定」の解釈 | 日付範囲指定で確定。基幹連携なし |
| カート | スマレジ・リピート |
| 商品コード | タグで受け渡し可 → 集計の一次キーに採用 |
| 規模 | 月間 1 万 PV → PostgreSQL 一本。100 倍まで現構成 |
| 提供形態 | SaaS マルチテナント |

| サンクスページへの JS タグ設置 | **可能**（独自差し込み変数も使える）→ S2S 連携は不要 |
| 初期導入サイト | `https://www.primedirect.jp/`（プライムダイレクト） |

### 未解決（Phase 0 で確定させる）

1. **カート / サンクスページのホスト名**（同一 or 別）— ビュースルー CV の可否が決まる ← 最優先
2. **差し込み変数の正確な変数名** — CV タグの実装に直結
3. **カート URL へのクエリパラメータ付与可否** — `pz_t` の可否（1 が別ホストの場合のみ）
4. **CV の定義** — 初回注文のみ（推奨） / 定期申込のみ / 全注文
5. **CV 地点の範囲** — 購入完了のみか、カート到達・定期申込も副次 CV として取るか

### 事業面で決めるべきこと

6. **プラン設計** — 料金体系、imp クォータ、機能差（holdout / S2S CV / CSV 出力）
7. **初期顧客** — 自社 EC で先行運用してから外販するか、最初から複数社に提供するか
8. **代理店機能の要否** — スキーマ上は対応済みだが、UI をいつ作るか
