# 08. 開発フェーズ / リスク

## 1. フェーズ計画

### Phase 1 — MVP（配信と計測が回る）

目標: 1 サイトで実配信し、imp / click / CV が管理画面で見られる。

- [ ] 設置タグ（ローダ）+ SDK 基盤（Shadow DOM 描画、フェイルセーフ）
- [ ] トリガー: `exit_back` / `dwell`
- [ ] 表示位置: PC 4 種 + SP 中央
- [ ] 対象ページ URL ルール（include / exclude）
- [ ] クリエイティブ複数登録 + 均等配信
- [ ] 画像アップロード + 自動最適化（WebP / 2x）
- [ ] 管理画面: キャンペーン CRUD、SP/PC プレビュー
- [ ] 計測: imp / click / cv（クリックスルーのみ）
- [ ] レポート: 期間指定 × クリエイティブ別
- [ ] フリークエンシー制御

想定: 2〜3 ヶ月 / フロント 1 名 + バック 1 名 + デザイン 0.5 名

### Phase 2 — 運用に耐える

- [ ] ページグループ（商品別レポート）
- [ ] トリガー追加: `exit_intent` / `scroll` / `idle`
- [ ] ビュースルー CV
- [ ] 対照群（holdout）と増分効果レポート
- [ ] CSV エクスポート、前期間比較
- [ ] タグ設置チェッカー
- [ ] 権限管理、複数サイト対応
- [ ] AVIF 対応、画像バリデーション警告

### Phase 3 — 拡張

- [ ] S2S コンバージョン API
- [ ] A/B テストの有意差判定 UI
- [ ] スケジュール配信（曜日・時間帯）、地域ターゲティング
- [ ] SP 下部固定バー、スライドイン等の表示形式追加
- [ ] メール取得フォーム型ポップアップ
- [ ] Shopify / EC-CUBE / futureshop 等のアプリ・プラグイン化
- [ ] ClickHouse への移行（イベント量に応じて）

## 2. 主要な設計上の意思決定と根拠

| 決定 | 根拠 | 代替案と却下理由 |
| --- | --- | --- |
| 設定を CDN に全量配信し判定はクライアント | 往復ゼロで表示遅延を排除。CDN で全ユーザー共通キャッシュ可 | 毎回サーバ判定 → レイテンシと負荷、キャッシュ不可 |
| クリエイティブ割当のみ Edge の Redis で決定 | 厳密な均等配信を担保 | 完全クライアント乱択 → 少数配信時に偏る（フォールバックとしては採用） |
| Shadow DOM (closed) | 顧客サイト CSS との相互汚染をゼロにする | iframe → 高コスト・レスポンシブ調整が困難 |
| renderer を SDK と管理画面で共有 | プレビューと本番の乖離を構造的に排除 | 管理画面で別実装 → 見た目のズレが恒常的なバグ源になる |
| 対照群を最初から設計に入れる | 「本当に増えたか」は差分でしか測れない | クリック経由 CV のみ → 効果を過大評価する |
| ブラウザバックは 1 回のみトラップ | ダークパターン回避・ブラウザのペナルティ回避 | 無限トラップ → UX 毀損、離脱率悪化 |
| 集計はロールアップ参照 | レポート応答を安定させる | 生イベント直クエリ → データ増でタイムアウト |

## 3. リスクと対策

| リスク | 影響 | 対策 |
| --- | --- | --- |
| SPA サイトで `pushState` 競合 | 顧客サイトのルーティング破壊 | 自前 state を判別。サイト単位で `exit_back` を無効化できる設定を用意。導入時に検証手順を提供 |
| 顧客サイトの JS エラーに巻き込まれる | サイト全体が壊れたように見える | 全エントリポイント try/catch、例外時は自己 teardown、Sentry へ送信 |
| 広告ブロッカーによる計測欠損 | 実績が過小に見える | 計測ドメインを 1st-party サブドメイン CNAME にできる構成。欠損率の推定値を管理画面に表示 |
| ITP による CV ウィンドウ短縮 | Safari で CV が取りこぼされる | S2S CV API を提供。管理画面で注意喚起 |
| ポップアップによる Core Web Vitals 悪化 | 顧客サイトの SEO 影響 | fixed レイヤのみで CLS 0、LCP 確定後にロード、Lighthouse 検証を CI に組込み |
| Google の「煩わしいインタースティシャル」ペナルティ | 顧客サイトの検索順位 | 初期表示直後の全画面表示を禁止（最短 3 秒待機のバリデーション）、SP は画面の 30% 以下を推奨としてガイド |
| 顧客サイトからのなりすまし計測 | データ汚染 | `allowed_hosts` 検証、レート制限、署名付き設定バージョン |
| イベント量増によるコスト増 | 運用コスト | サンプリング（imp のみ）を将来オプションとして用意、13 ヶ月で生ログ削除 |

## 4. リポジトリ構成（案）

```
popup/
├─ apps/
│  ├─ admin/            Next.js 管理画面
│  ├─ api/              管理 API
│  └─ edge/             /d /e Edge Functions
├─ packages/
│  ├─ loader/           t.js
│  ├─ sdk/              sdk.js
│  ├─ renderer/         描画（SDK と admin で共有）★
│  ├─ shared/           型定義・URL マッチャ・バリデータ（サーバ/クライアント共有）★
│  └─ image/            最適化パイプライン
├─ services/
│  └─ aggregator/       集計バッチ
├─ db/
│  ├─ migrations/
│  └─ seeds/
├─ e2e/                 Playwright（実サイト模擬ページで表示・計測を検証）
└─ docs/
```

★ の 2 パッケージが品質の要。
URL マッチロジックを `shared` に置き、**管理画面のマッチ判定ツール・SDK の配信判定・
サーバ側の検証で同一コードを使う**ことで、「管理画面ではマッチしたのに配信されない」を防ぐ。

## 5. テスト方針

| レイヤ | 手法 |
| --- | --- |
| URL マッチャ / フリークエンシー / アトリビューション | ユニットテスト（境界値重点） |
| 均等配信 | 10,000 回シミュレーションで偏りが ±1% 以内 |
| SDK 表示 | Playwright で PC/SP viewport × 位置 4 種のビジュアルリグレッション |
| トリガー | Playwright で `goBack()` / タイマー / mouseout を実行し発火を検証 |
| 計測 | モックサーバでイベントペイロードを検証。重複排除の冪等性テスト |
| 集計 | 既知イベント列 → 期待ロールアップ値のゴールデンテスト |
| 性能 | Lighthouse CI でタグ有無の LCP / CLS 差分を監視 |

## 6. 次に決めるべきこと

1. 「基幹指定」の解釈確認（**期間指定**と解釈して設計 / 基幹システム連携が必要か）
2. 対象 EC カート（Shopify / EC-CUBE / 独自 / 複数）— タグ設置方法とプラグイン化の要否
3. 商品コードをタグから渡せるか（渡せない場合は URL ルールのみで商品別レポートを構成）
4. 想定 imp 規模（月間）— DB 選定（Postgres 一本 か ClickHouse 併用）の分岐点
5. CV 地点の定義（購入完了のみ / 会員登録・カート投入も含むか）
6. マルチテナント要否（自社 EC 専用 か SaaS として複数社に提供するか）
